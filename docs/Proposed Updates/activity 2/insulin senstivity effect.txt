Overall verdict
The plan is correct and the constraint of "zero breaking changes" is achievable. The gap you've identified is real: activitySensitivityMultiplier makes it all the way into the return object of calculateNetEffectAtTime (stored as activitySensitivityMultiplier) but is never multiplied into insulinImpact or its cumulative counterpart. Everything downstream just reads the un-boosted values.

Refinements per phase
Phase 1 — netEffectCalculationService.js
Your split logic is right, but there are two subtleties worth nailing upfront:
1a. What insulinImpact should represent in the return value.
The cleanest contract for the rest of the codebase is: insulinImpact = the total boosted value (base × multiplier). That way netEffect = mealImpact + insulinImpact automatically accounts for the boost, and cumulativeNetBaseline stays accurate without any callers needing to know about the split. The split fields (insulinImpactBase, insulinSensitivityBoost) are additive, not replacements.
js// Inside calculateNetEffectAtTime, after insulinImpact is computed:
const insulinImpactBase  = insulinImpact;                                  // base, no exercise
const insulinImpactBoosted = insulinImpactBase * activitySensitivityMultiplier;  // total
const insulinSensitivityBoost = insulinImpactBoosted - insulinImpactBase;  // extra drop (also negative)

// Replace the returned insulinImpact with the boosted total:
// return { ..., insulinImpact: insulinImpactBoosted, insulinImpactBase, insulinSensitivityBoost }
This means netEffect = mealImpact + insulinImpactBoosted which is the correct physiology — more exercise → ISF goes up → same absorbed insulin drops BG more.
1b. pendingInsulinReduction also needs the multiplier. This field is totalActiveInsulin * correctionFactor and it feeds the projected BG calculations in calculateProjectedFinalBG. If IOB will clear at boosted ISF, ignoring this understates predicted hypo risk — particularly in the 1–3 h post-vigorous window where AOB and IOB overlap. Suggest adding pendingInsulinReductionBoosted = pendingInsulinReduction * activitySensitivityMultiplier and using the boosted value in projections.
1c. cumulativeInsulinEffect split. Your plan mentions this but the implementation needs care. Since calculateNetEffectAtTime is called per-tick and the multiplier is already available as activitySensitivityMultiplier at that tick, the simplest correct approach is:
jsconst cumulativeInsulinEffectBase    = cumulativeInsulinEffect;           // existing
const cumulativeInsulinEffectBoosted = cumulativeInsulinEffectBase * activitySensitivityMultiplier;
// Update cumulativeNetBaseline to use the boosted value
const cumulativeNetBaseline = cumulativeMealEffect + cumulativeInsulinEffectBoosted + cumulativeActivityEffect;
No double-counting risk: cumulativeActivityEffect is the direct BG drop from exercise (via IIRd/W-window PD model). The sensitivity boost is the indirect amplification of existing insulin — these are physiologically separate and should both be in the balance.

Phase 3 — Recharts <Area> stacking
Recharts stackId with two negative-value series stacks them additively in the negative direction, which is exactly what you want. The purple area fills from 0 → insulinImpactBase, the rose area extends the fill from there to insulinImpact (total). The combined visual footprint equals the full boosted effect.
jsx<Area
  dataKey="insulinImpactBase"
  stackId="insulin"
  fill="#9c27b0"   // existing purple
  stroke="#9c27b0"
  name="Insulin (base)"
  connectNulls
/>
<Area
  dataKey="insulinSensitivityBoost"
  stackId="insulin"
  fill="#E91E8C"   // rose/magenta as planned
  stroke="#E91E8C"
  name="Sensitivity boost"
  fillOpacity={0.7}
  connectNulls
/>
One practical concern: when sensitivityMultiplier === 1.0 (no active exercise effect), insulinSensitivityBoost === 0. Recharts handles zero-valued stacked areas cleanly, so no null/conditional rendering is needed — the rose area simply disappears.

One suggested Phase 0 (before Phase 1)
Add an integration test fixture before touching any logic. Create a snapshot of calculateNetEffectAtTime({ ..., activityPD: { sensitivity_multiplier: 1.3, ... } }) with a known insulin dose, and assert that insulinImpact === base × 1.3 and insulinSensitivityBoost === base × 0.3. This protects against silent regressions when future refactors touch the multiplier path — the current code has a latent bug that's invisible precisely because the multiplier was never applied.
